What is an API?

Before you learn CORS, Middleware, REST, or SOAP — you need to understand what an API actually is. Everything on this page builds on this one idea.

The simplest explanation

API = Application Programming Interface. That's the full form. But the words don't tell you much. Here's the plain version:

An API is a way for two programs to talk to each other. One program asks for something. The other program responds. That's it.

🔌 The power socket analogy

Think of an electrical socket in your wall. You don't need to know how the power station works, how the wires run through your building, or how electricity is generated. You just plug in your phone charger and it works.

The socket is the interface. It's the agreed-upon point of connection. Your charger knows what shape the plug is, what voltage to expect — and that's all it needs.

An API works the same way. One side offers a socket (the API). The other side plugs in (makes a request). Neither side needs to know how the other works internally.

A real everyday example

You open Swiggy on your phone and search for "pizza near me." Here's what actually happens:

  1. Your Swiggy app sends a request to Swiggy's API: "Give me pizza restaurants near location 17.4N, 78.4E"
  2. Swiggy's servers receive that request, search their database, and prepare a response
  3. The API sends back a list of restaurants with names, ratings, prices, and delivery times
  4. Your app displays that data as cards on your screen

The Swiggy app doesn't store restaurant data. It asks for it via an API every time you search. The app and the server are two separate programs communicating through a well-defined interface.

Why do APIs exist?

Three fundamental reasons:

1. Separation of concerns

Your frontend (what users see) and your backend (where data lives) can be built by different teams, in different languages, deployed independently — because they talk through an agreed API. Change the backend completely without touching the frontend.

2. Reusability

One API, many consumers. Swiggy's API is used by the Android app, the iOS app, the website, and third-party partners — all at the same time. Write the logic once, expose it via an API, and anyone can use it.

3. Security and control

You never expose your database directly to the internet. Instead, you expose an API that sits in front of it. The API decides who can access what, validates every request, and logs everything. Your actual data stays protected.

How an API call works — the basic flow

1
Client makes a request

Your app (the client) sends a message to a URL — called an endpoint. The message includes what you want and any data needed to get it.

2
Server processes it

The server receives the request, runs the logic (queries the database, calculates something, calls another API), and prepares a response.

3
Server sends a response

The server replies with data (usually JSON) and a status code that tells the client whether it worked or not.

✓
Client uses the data

Your app reads the response and displays the results, updates the UI, or acts on the data.

7const data = await response.json();
8console.log(data.restaurants); // array of restaurant objects

Types of APIs you'll encounter

Not all APIs are built the same way. Different styles exist for different needs. Here are the four main types:

🌐
REST API Most common · Covered in this guide

Uses standard HTTP methods (GET, POST, PUT, DELETE) and JSON. This is what 90% of modern web and mobile apps use. Instagram, GitHub, Swiggy, YouTube — all REST.

📄
SOAP API Enterprise · Covered in this guide

Uses XML and strict contracts (WSDL). Older but still dominant in banking, government, and healthcare. Heavier than REST but built-in security standards.

⚡
GraphQL Not covered here

Created by Facebook. You write a query that describes exactly what data you want — no more, no less. Used by GitHub, Shopify, Twitter. Great for complex data relationships.

🚀
gRPC Not covered here

Created by Google. Uses binary format (Protocol Buffers) instead of JSON — much faster and smaller. Popular for internal microservice communication where speed is critical.

01 Topic · CORS

Cross-Origin Resource Sharing

Why does your fetch request fail with that scary red error in the browser console, even though the API works in Postman? Welcome to CORS.

The apartment security analogy

Imagine you live in a gated apartment complex. A friend wants to come visit. They walk up to the gate and the watchman stops them: "Wait — you don't live here. Who are you here to see?" Your friend has to declare their identity and the watchman has to verify it before letting them in.

Now imagine the watchman has a list pinned to the wall — a list of people who are pre-approved. If your friend's name is on the list, they walk right in. If it's not, they get blocked at the gate.

🏢 The mental model

The apartment = your backend server

The visitor = a website making a request to your server

The watchman = the browser, enforcing rules

The approved list on the wall = the Access-Control-Allow-Origin header your server sends back

What is an "origin"?

An origin is the combination of three things: protocol + domain + port. If any one of those differs between two URLs, they have different origins.

  • https://shop.com and http://shop.com → different (protocol differs)
  • https://shop.com and https://api.shop.com → different (subdomain differs)
  • https://shop.com:443 and https://shop.com:8080 → different (port differs)
  • https://shop.com/cart and https://shop.com/about → same (only path differs, which doesn't count)

The Same-Origin Policy — and why it exists

By default, browsers do not allow a script running on shop.com to make requests to bank.com. This rule is called the Same-Origin Policy, and it's been baked into browsers since the late 90s.

Why? Imagine you're logged into your bank in one tab. You open a sketchy site in another tab. Without this rule, that sketchy site's JavaScript could quietly send a request to your bank's API using your cookies and transfer money. The Same-Origin Policy stops this.

⚠️ Important: CORS is enforced by the browser, not the server

If you call the same API from Postman, curl, or a Python script, it works fine. CORS errors only appear when a browser is in the middle. The server still sends the response — the browser just refuses to give it to your JavaScript.

CORS: the official "permission slip" system

The Same-Origin Policy is too strict in practice. Frontend on shop.com almost always needs to call its API on api.shop.com. So CORS was invented as the official way for a server to say: "It's okay, I trust requests from these specific origins."

The server includes a special header in its response:

response headers
1Access-Control-Allow-Origin: https://shop.com
2Access-Control-Allow-Methods: GET, POST, PUT, DELETE
3Access-Control-Allow-Headers: Content-Type, Authorization
4Access-Control-Allow-Credentials: true

The browser reads these headers and decides whether to release the response to your JavaScript or block it.

Preflight requests (the OPTIONS dance)

For "simple" requests (basic GET/POST with standard headers), the browser sends the request and then checks CORS headers in the response. Easy.

But for anything "non-simple" — PUT, DELETE, requests with custom headers like Authorization, or content types like application/json — the browser does something extra. Before the real request, it sends a "preflight" request using the OPTIONS method to ask the server: "Hey, I'm about to send a PUT request with these headers. Will you accept it?"

If the server's preflight response says yes, the real request goes through. If not, the real request is never even sent.

🔄 The preflight flow

1. Browser sends OPTIONS /api/users with headers describing the upcoming request

2. Server responds with Access-Control-Allow-* headers saying what's permitted

3. If allowed, browser sends the real PUT /api/users

4. If blocked, browser cancels everything and shows the CORS error

Fixing CORS in popular frameworks

FastAPI · main.py
1from fastapi import FastAPI
2from fastapi.middleware.cors import CORSMiddleware
3
4app = FastAPI()
5
6app.add_middleware(
7 CORSMiddleware,
8 allow_origins=["https://shop.com"],
9 allow_credentials=True,
10 allow_methods=["*"],
11 allow_headers=["*"],
12)
Express.js · server.js
1const cors = require('cors');
2const app = express();
3
4app.use(cors({
5 origin: 'https://shop.com',
6 credentials: true,
7 methods: ['GET', 'POST', 'PUT', 'DELETE'],
8}));
⚠️ Common CORS mistakes

Using allow_origins=["*"] with credentials. The wildcard * can never be combined with credentials. You must specify exact origins.

Putting CORS middleware in the wrong order. In Express, it must come before your routes. In FastAPI, it should be added before app.include_router().

Forgetting the protocol. shop.com and https://shop.com are not the same. Always include the scheme.

Assuming localhost will work. If your frontend is on http://localhost:3000 and backend on http://localhost:8000, those are different origins. You still need CORS configured.

🎯 CORS in one sentence

CORS is the browser's way of asking a server "is this origin allowed to read your response?" — and the server answers with HTTP headers. Fix CORS by configuring those headers on your server, not by changing the browser.

02 Topic · Middleware

Middleware — the request pipeline

Every request flows through a chain of checkpoints before it reaches your code. Each checkpoint can inspect it, modify it, block it, or let it pass. That's middleware.

The airport security analogy

You arrive at the airport with a flight to catch. Before you reach the boarding gate, you go through a sequence of checkpoints. Each one has a single job. Each one can stop you if something's wrong.

  • Check-in counter — verifies your ticket exists. No ticket? You're stopped here.
  • ID verification — confirms your face matches your ID. Mismatch? Stopped.
  • Baggage scan — checks your bags for prohibited items. Found something? Stopped.
  • Body scanner — final security check.
  • Boarding gate — only now do you reach the actual plane.

If any checkpoint rejects you, you never reach the plane. If you pass all of them, you board. Middleware in a backend works exactly the same way.

What middleware actually is

Middleware is a function that sits between the incoming request and your route handler. It gets the request, can do something with it, and then either passes it to the next middleware (or your handler) or stops the request right there.

🛂 The mental model

Request = passenger at the airport

Middleware = each security checkpoint

Route handler = the actual plane (the destination)

next() = "you passed, continue to the next checkpoint"

Common middleware types

  • Logging middleware — records every request: who, when, what endpoint, how long it took. Essential for debugging production.
  • Authentication middleware — checks "who are you?" by validating tokens, cookies, or API keys.
  • Authorization middleware — checks "what are you allowed to do?" by inspecting roles or permissions.
  • Rate limiting middleware — stops abuse by counting how many requests a single client has made.
  • CORS middleware — yes, the CORS we just covered is itself a middleware.
  • Body parser — converts raw JSON or form data into a usable Python/JS object.
  • Error handler — catches any error from earlier middleware or the route handler and returns a clean response.

The request-response lifecycle

A complete cycle looks like this:

  1. Request arrives at the server
  2. Middleware 1 (e.g., logger) runs → calls next()
  3. Middleware 2 (e.g., auth) runs → calls next()
  4. Middleware 3 (e.g., rate limit) runs → calls next()
  5. Route handler runs, generates the response
  6. Response flows back through middleware in reverse
  7. Response is sent to the client

The "back through in reverse" part is important. If your logging middleware wants to record the response status, it gets a chance after the handler runs.

Middleware in Express.js

express-middleware.js
1const app = express();
2
3// 1. Logger middleware — runs for every request
4app.use((req, res, next) => {
5 console.log(`${req.method} ${req.url}`);
6 next(); // pass to the next middleware
7});
8
9// 2. Auth middleware — checks token
10app.use((req, res, next) => {
11 if (!req.headers.authorization) {
12 return res.status(401).send('No token');
13 }
14 next();
15});
16
17// 3. Actual route — runs only if all middleware passed
18app.get('/profile', (req, res) => {
19 res.json({ user: 'Aarav' });
20});

Middleware in FastAPI

2import time
3
4app = FastAPI()

7async def log_requests(request: Request, call_next):
8 start = time.time()
9 response = await call_next(request) # run rest of pipeline

11 print(f"{request.method} {request.url} took {duration:.3f}s")

15def get_items():

⚠️ Order matters

Middleware runs in the order you register it. If you put your route handler before your auth middleware, the route handler runs first and auth never gets to check anything. Always: logging → CORS → body parsing → auth → rate limiting → routes → error handler.

🎯 Middleware in one sentence

Middleware is a pipeline of small functions that every request flows through. Each one does one job — log, authenticate, validate, rate-limit — and either passes the request along or stops it cold.

03 Topic · REST API

REST APIs — how the web talks

Every app on your phone is constantly making REST API calls. Once you learn the basics, you can build the same kind of communication into anything.

The restaurant analogy

You walk into a restaurant. You sit down. A waiter brings you a menu. You order "one masala dosa." The waiter writes it down, walks to the kitchen, gives the order to the chef. The chef cooks. The waiter brings the dosa back to your table.

You never set foot in the kitchen. You don't know which stove the dosa was made on, what brand the gas cylinder is, or what the chef looks like. All you needed was the menu (the list of things you can order) and the waiter (a reliable middleman).

🍽️ The mental model

You = the client (frontend app, mobile app, another server)

Menu = the API documentation (what you can request)

Waiter = the REST API (the agreed-upon way to ask)

Kitchen = the backend server (where the actual work happens)

Dosa = the response (the data you get back)

What "REST" actually stands for

REST = Representational State Transfer. That's a mouthful and not very enlightening on its own. The practical definition: REST is a set of conventions for designing APIs so that anyone can use them without needing custom instructions.

If your API follows REST conventions, another developer can pick up your docs and figure it out in minutes. The conventions are:

  • Use HTTP methods (GET, POST, PUT, DELETE) to describe what kind of operation you want
  • Use URLs to identify the resource you're operating on
  • Use status codes in the response to tell the client what happened
  • Use JSON (usually) as the data format
  • Be stateless — every request contains everything the server needs; no hidden memory between calls

Resources and endpoints

In REST, you think in terms of resources. A resource is a "thing" your API deals with — users, orders, products, posts, comments. Each resource gets its own URL, and you use HTTP methods to do things to it.

RESTful URL design
1# Collection of users
2GET /users # list all users
3POST /users # create a new user
4
5# A specific user
6GET /users/42 # get user with id 42
7PUT /users/42 # replace user 42 fully
8PATCH /users/42 # update some fields of user 42
9DELETE /users/42 # delete user 42
10
11# Nested resources
12GET /users/42/orders # all orders by user 42
13POST /users/42/orders # create an order for user 42

Status codes — the server's reply category

Every HTTP response includes a 3-digit status code. The first digit tells you the category:

  • 2xx — Success. 200 OK (generic success), 201 Created (new resource made), 204 No Content (success, nothing to return).
  • 3xx — Redirection. 301 Moved Permanently, 304 Not Modified (use your cached version).
  • 4xx — Client error. You messed up. 400 Bad Request, 401 Unauthorized (no auth), 403 Forbidden (auth but not allowed), 404 Not Found, 429 Too Many Requests (rate-limited).
  • 5xx — Server error. The server messed up. 500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable.

🎯 REST in one sentence

REST is a set of conventions for designing web APIs: use HTTP methods to describe the action, URLs to identify resources, status codes to describe the result, and JSON to carry data. Follow the conventions and any developer can use your API without reading custom instructions.

04 Topic · FastAPI

FastAPI — modern Python APIs

Now that you understand REST, let's actually build an API. FastAPI is the modern Python framework for it — fast to write, fast to run, and gives you auto-generated docs for free.

Why FastAPI exists

Python has had Flask and Django for years. So why another framework? Three reasons FastAPI took off:

  • Speed. Built on Starlette and async Python, it's one of the fastest Python frameworks — comparable to Node.js and Go.
  • Less code. Type hints do double duty as validation. You write Python types; FastAPI uses them to validate incoming requests automatically.
  • Free interactive docs. Visit /docs on any FastAPI app and you get a full Swagger UI generated automatically from your code. No extra config.
💡 The pitch

FastAPI gives you the structure of a heavyweight framework (validation, docs, async) with the lightweight feel of Flask. For new Python APIs in 2026, it's the default choice.

The smallest possible API

This is a complete, working FastAPI app:

main.py
1from fastapi import FastAPI
2
3app = FastAPI()
4
5@app.get("/")
6def root():
7 return {"message": "Hello, world"}

Run it with uvicorn main:app --reload. Open http://localhost:8000 in a browser → you get the JSON response. Open http://localhost:8000/docs → you get an interactive API tester. Zero extra setup.

SOAP — the strict ancestor of REST

      
You'll rarely build a new SOAP API in 2026. But banks, governments, and legacy enterprise systems still run on it. Knowing SOAP makes you valuable in places no one wants to touch.

    


    


      

        
The registered courier analogy

        
When you send a regular WhatsApp message, you type and tap send. Casual. Fast. If it gets delivered, great. If not, you might or might not be notified.

        
Now compare that to sending a registered courier through Speed Post. You fill out a printed form with the sender details, receiver details, weight, contents, declared value, signature, and a unique tracking number. The post office stamps it. The recipient must sign for it. Every step is documented. Every step can be audited.

        
REST is the WhatsApp message. SOAP is the registered courier — slower, heavier, more paperwork, but every detail is verified and traceable. Banks and governments like that.

        

          
📮 The mental model

          

            
SOAP = strict, verbose, XML-based, with built-in standards for security, transactions, and error handling.

            
REST = flexible, lightweight, JSON-based, leaves most decisions to you.

            
SOAP feels like overkill for a normal app. For a bank-to-bank money transfer, the strictness is the point.

          

        

      


      

        
What SOAP stands for

        
SOAP = Simple Object Access Protocol. Don't be fooled by "simple" — it's anything but. SOAP was designed in the late 1990s as a way for programs on different machines (different OSes, different languages, different vendors) to talk to each other reliably using XML.

        
The "simple" referred to the original goal: stop forcing developers to write custom binary protocols for every integration. Use XML over HTTP and let it work everywhere.

      


      

        
The structure of a SOAP message

        
Every SOAP message is an XML document with a specific shape. Three main parts:

        
    
          
  • Envelope — the outermost wrapper. It tells the receiver "this is a SOAP message."
    • 
          
  • Header (optional) — metadata like authentication tokens, transaction IDs, routing info.
    • 
          
  • Body — the actual payload: what you're asking for or what you got back.
    • 
        

        
If something went wrong, the body contains a Fault element instead — SOAP's standardized way of reporting errors.

WSDL — the contract

        
SOAP services come with a WSDL (Web Services Description Language) document. It's another XML file that formally describes everything the service offers: every operation, every parameter, every data type, every endpoint.

        
Why does this matter? Because given a WSDL, your tooling can automatically generate client code. You point a tool at the WSDL URL and it spits out a fully typed Python or Java class you can call directly. No reading docs, no guessing field names. Whereas REST APIs typically require you to read the docs and write the client by hand (or use OpenAPI for similar generation).

SOAP is the strict, XML-based, contract-first protocol used by enterprise systems where reliability and standardization matter more than speed or simplicity. You won't build many SOAP APIs today, but you'll meet one eventually.

      Quick reference
      
Cheatsheet — all 5 topics

      
Bookmark this page. Come back when you forget a syntax. Everything here in one glance.

    

    

      

        
01 · CORS

        
Allow cross-origin

        
Set headers on the server, not the browser.

        
Access-Control-Allow-Origin: https://shop.com
Access-Control-Allow-Methods: GET, POST, PUT
Access-Control-Allow-Credentials: true

      

      

        
02 · Middleware

        
Request pipeline

        
Order: log → CORS → parse → auth → routes → errors.

        
app.use((req, res, next) => {
  console.log(req.url);
  next(); // continue
});

      

      

        
03 · REST

        
HTTP methods

        
GET=read · POST=create · PUT=replace · PATCH=update · DELETE=remove.

        
GET    /users      // list
POST   /users      // create
GET    /users/42   // one
DELETE /users/42   // remove

      

      

        
04 · FastAPI

        
Quick API

        
Type hints = validation. /docs free.

        
@app.get("/items/{id}")
def read(id: int):
    return {"id": id}

      

      

        
05 · SOAP

        
XML envelope

        
Envelope → Header → Body. Strict, contract-first.

        
<soap:Envelope>
  <soap:Header>...</soap:Header>
  <soap:Body>...</soap:Body>
</soap:Envelope>
