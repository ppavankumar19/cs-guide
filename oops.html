Chapter 1 · Foundations

Before OOP: what is programming?

If you can give directions, you can write a program. Programming is just instructions written in a language computers understand.

🍕

Food delivery

When you order food on an app: select restaurant, pick items, confirm address, pay. Each tap is an instruction. The app strings them together into a program.

🏧

ATM withdrawal

Insert card, enter PIN, choose amount, take cash. The ATM follows a written sequence of instructions every single time. That sequence is a program.

🚂

Booking a ticket

Select route, pick date, choose seat, enter passenger details, pay. Behind the scenes a program checks availability, locks the seat, sends confirmation.

☕

Ordering coffee

"One latte, oat milk, no sugar, extra hot." That's a specification. Programming is writing specifications a computer can follow without confusion.

💡 Key insight

Programming = giving precise, ordered instructions to a computer. The hard part isn't the syntax — it's being precise. Computers do exactly what you tell them, no more, no less. That's why we need ways to organize instructions cleanly. Which brings us to OOP.

Core concept

Class & Object

A class is a blueprint. An object is something built from that blueprint. Get this one right and the rest of OOP becomes much easier.

The everyday analogy

Think about how a tea shop works. The owner has a recipe written in their head — how much tea leaves, sugar, milk, and water to use, and how long to boil. That recipe is not a cup of tea. You can't drink it. It's just instructions.

Now when a customer orders, the owner follows the recipe and makes an actual cup. That cup is a real, drinkable thing. They can make ten cups, a hundred cups — each one a separate physical cup, but all made from the same recipe.

✨ The mental model

Recipe = Class. A definition. A template. It describes what something is and what it can do, but it isn't a thing itself.

Cup of tea = Object. A real, concrete instance made from the class. Each object has its own values for the attributes the class defined.

What goes inside a class

Every class has two kinds of things inside it:

  • Attributes — the data each object holds. For a Tea class: sugar, milk, tea_type. For a Student class: name, marks, class_name.
  • Methods — the actions each object can perform. A Tea object might serve() or add_sugar(). A Student might study() or take_exam().

Attributes are "what an object has." Methods are "what an object can do." That's the whole picture.

Common mistakes to avoid

⚠️ Pitfalls

Forgetting self. Writing sugar = sugar inside __init__ creates a local variable that disappears. You must write self.sugar = sugar to actually save it on the object.

Confusing the class with the object. Tea is the class. cup1 is the object. You call methods on the object: cup1.serve(), not Tea.serve() (unless passing the object explicitly).

Naming the class lowercase. Python convention: classes use CapitalCase, functions and variables use snake_case. Following this makes your code instantly readable to other Python developers.

🎯 Key takeaway

A class defines a kind of thing. An object is one specific thing of that kind. You can create unlimited objects from one class, and each object holds its own data while sharing the same behavior (methods).

Core concept

The self keyword

This trips up almost every Python beginner. Once it clicks, OOP suddenly makes sense.

What is self?

self is just a reference to the current object. When you call cup1.serve(), Python silently passes cup1 as the first argument to serve(). Inside the method, that argument is called self.

So when you write self.sugar, you mean "the sugar value of this specific object." If cup1 called the method, self.sugar reads cup1.sugar. If cup2 called it, self.sugar reads cup2.sugar.

💡 In other words

self answers the question: "which object is this method working on right now?"

See it in action

self_demo.py
1class Dog:
2 def __init__(self, name):
3 self.name = name # attach 'name' to THIS dog
4
5 def bark(self):
6 print(f"{self.name} says: Woof!")
7
8a = Dog("Bruno")
9b = Dog("Max")
10
11a.bark() # self = a, so self.name = "Bruno"
12b.bark() # self = b, so self.name = "Max"
Output
› Bruno says: Woof!
› Max says: Woof!

Same method, two different results — because self refers to a different object each time.

📝 Three things to remember

1. Every method inside a class must take self as its first parameter (unless it's a static or class method, which we'll cover later).

2. You never pass self manually when calling a method. cup1.serve() — Python passes cup1 as self automatically.

3. The name self isn't reserved by Python — you could call it anything. But everyone uses self. Don't be the person who calls it this or me.

Core concept

The Constructor (__init__)

A special method that runs automatically every time you create an object. It sets up the object's starting state.

The new-phone analogy

When you buy a new phone, you don't get a blank slab. The moment you unbox and turn it on, a setup wizard appears: pick language, connect WiFi, sign in, transfer data. By the time you reach the home screen, the phone is ready to use.

The constructor does exactly this for an object. The moment you create an object, __init__ runs automatically and sets up everything the object needs.

Why "__init__"?

The name is short for initialize. The double underscores on both sides (__init__) signal that this is a special method Python recognizes — sometimes called a "dunder" method (for "double underscore"). You don't call __init__ yourself. Python calls it when you do Tea() or Student().

🎯 Key takeaways

1. __init__ runs automatically the moment you write ClassName(args). You never call it yourself.

2. Arguments to the class go to __init__. Phone("Samsung", "S25") passes "Samsung" as brand and "S25" as model — Python wires them up in order.

3. Use it to set up state. Anything the object needs to know from the start — attributes, defaults, connections — goes here.

4. Default values are allowed. Like any Python function: def __init__(self, name, age=18).

Pillar of OOP

Encapsulation

Bundle data with the code that uses it, and hide the parts that shouldn't be touched from outside. Think of it as putting your data in a protective capsule.

The ATM analogy

An ATM has two sides. The outside: a screen, a card slot, a keypad, a cash dispenser. That's what you, the user, interact with. Simple, safe, controlled.

The inside: PIN verification, balance lookup, ledger updates, fraud detection, encryption keys, network calls to the bank. You can't see any of it. You can't reach in and change the balance directly. You can't reset someone's PIN. The bank built walls around all that for very good reasons.

Encapsulation in code is the same idea: expose what users need, hide the internal mechanics that could break things if misused.

Public, protected, private

Python uses naming conventions to signal what's safe to touch from outside the class:

  • self.balance — public. Anyone can read or change it. Use for data that's safe to expose.
  • self._balance (one underscore) — protected. A convention: "this is internal, don't touch unless you know what you're doing." Python doesn't enforce it.
  • self.__balance (two underscores) — private. Python actually renames this internally (called name mangling) so it's hard to access from outside. Strong "stay out" signal.
Python's philosophy

Unlike Java or C++, Python doesn't have true private variables. The leading underscore is a polite agreement between programmers: "I marked this private, please don't poke at it." Python trusts adults to behave like adults.

atm.py
1class Account:
2 def __init__(self, balance, pin):
3 self.__balance = balance # private — can't access from outside
4 self.__pin = pin # private — definitely don't expose
5
6 def withdraw(self, pin, amount):
7 if pin != self.__pin:
8 return "Wrong PIN"
9 if amount > self.__balance:
10 return "Insufficient funds"
11 self.__balance -= amount # controlled change
12 return f"₹{amount} dispensed"
13
14 def get_balance(self, pin): # controlled read
15 return self.__balance if pin == self.__pin else "Access denied"
16
17acc = Account(10000, "1234")
18print(acc.withdraw("1234", 2000)) # works
19acc.__balance = 9999999 # sneaky — but doesn't work!
20print(acc.get_balance("1234")) # still 8000, not 9999999
🎯 Why encapsulation matters

Safety. Critical data can't be corrupted by accident or malicious code.

Control. Every change goes through a method, so you can validate, log, or restrict it.

Flexibility. You can change how data is stored internally without breaking code that uses your class.

Pillar of OOP

Abstraction

Show only what's necessary, hide everything else. Encapsulation hides data. Abstraction hides complexity.

The driving analogy

When you drive a car, you press the accelerator and the car speeds up. You press the brake and it slows down. You turn the steering wheel and it changes direction. Simple.

But underneath, the engine is firing pistons, the gearbox is shifting ratios, the brakes are applying hydraulic pressure, sensors are firing dozens of times per second. None of this is exposed to you. You don't need to understand any of it to drive.

That's abstraction. The car maker built a simple interface over a complex machine. You can use it without understanding it.

Encapsulation vs Abstraction

These two get confused often. Here's the cleanest way to remember:

  • Encapsulation hides data. It's about protecting your variables from outside interference.
  • Abstraction hides implementation. It's about exposing a simple interface over complex logic.

They usually work together. An ATM encapsulates the balance (data) and abstracts the banking network (complexity) behind a 4-button interface.

Abstract classes in Python

Python has a tool called ABC (Abstract Base Classes) that lets you define a class that can't be used directly — it can only be a parent for other classes. It forces child classes to implement specific methods.

vehicle.py
1from abc import ABC, abstractmethod
2
3class Vehicle(ABC): # abstract class — can't make objects from this
4 @abstractmethod
5 def start(self): # child MUST implement this
6 pass
7
8 @abstractmethod
9 def stop(self):
10 pass
11
12class Car(Vehicle):
13 def start(self): # implementation required
14 print("Engine started, ready to drive")
15 def stop(self):
16 print("Engine off")
17
18v = Vehicle() # TypeError — can't instantiate abstract class
19c = Car() # works fine
20c.start() # Engine started, ready to drive
🎯 Key takeaways

Abstraction is about interface design. Good abstraction means a user can do useful things with your class without reading its source code.

Abstract classes force a contract. They say: "any class that inherits from me must provide these methods." This is great for consistency in larger systems.

You can't instantiate an abstract class. They exist only to be inherited from.

Pillar of OOP

Inheritance

Build new classes from existing ones. A child class gets everything its parent has, then adds or changes what it needs.

The family analogy

You inherit traits from your parents — eye color, height, surname, maybe a tendency to laugh too loudly. You didn't have to build those from scratch; they came with you. Then you add your own personality on top.

In OOP, a child class inherits all the attributes and methods of its parent class. The child can use them as-is, add new ones, or override existing ones with its own version.

The "is-a" relationship

Inheritance models the "is-a" relationship. A Car is a Vehicle. A Dog is an Animal. A Manager is an Employee. Whenever you can naturally say "X is a Y," inheritance might be the right tool.

⚠️ When NOT to use inheritance

If you find yourself saying "X has a Y" instead of "X is a Y," use composition instead (we'll cover it next). A car has an engine — but a car is not an engine. So Car shouldn't inherit from Engine. Beginners often misuse inheritance for code reuse, which leads to brittle designs.

Inheritance in Python

vehicle_hierarchy.py
1class Vehicle: # Parent class
2 def __init__(self, brand):
3 self.brand = brand
4
5 def start(self):
6 print(f"{self.brand} is starting...")
7
8class Car(Vehicle): # Car inherits from Vehicle
9 def __init__(self, brand, seats):
10 super().__init__(brand) # call parent's __init__
11 self.seats = seats # Car-specific attribute
12
13 def open_trunk(self): # Car-specific method
14 print("Trunk opened")
15
16my_car = Car("Tesla", 5)
17my_car.start() # inherited from Vehicle
18my_car.open_trunk() # defined in Car
19print(my_car.brand) # 'Tesla' — inherited attribute
Output
› Tesla is starting...
› Trunk opened
› Tesla

About super()

When a child overrides __init__ (or any method), it often still needs the parent's setup to run. super().__init__(brand) means "call the parent's __init__ with this argument." Skipping it means the parent's attributes never get set, and you'll hit confusing errors later.

Types of inheritance

  • Single inheritance — one parent, one child. Most common.
  • Multilevel — grandparent → parent → child. Like our tree above.
  • Hierarchical — one parent, many children. Vehicle has Car, Truck, Bike all inheriting from it.
  • Multiple inheritance — one child has multiple parents. Powerful but can get messy (look up "diamond problem"). Use sparingly.
🎯 Key takeaways

Inheritance lets you reuse and extend. Define common code once in a parent, then specialize in children.

Use it for "is-a" relationships only. Not for "has-a" — that's what composition is for.

Call super() when overriding if you still need parent behavior.

Polymorphism & Method Overriding

One method name. Many different behaviors. Polymorphism literally means "many forms."

The payment app analogy

Three different payment apps — Google Pay, PhonePe, Paytm — all have a button called "Pay." From your perspective, the action is identical: tap, enter amount, confirm. But behind the scenes, each app does something completely different. Different protocols, different banking partners, different security flows.

That's polymorphism. Same method name, different implementations depending on which object you're calling it on.

11 print(f"₹{amount} via PhonePe wallet")

15 app.pay(100)

Method Overriding — cricket commentary

Same event, different commentary. That's overriding: a child class provides its own version of a method that already exists in the parent.

Method Overriding vs Polymorphism

These are closely related but not identical:

  • Method overriding is the mechanism: a child class redefines a method from its parent.
  • Polymorphism is the capability this enables: code that calls obj.pay() works no matter which payment app obj happens to be.

Overriding is how you do it. Polymorphism is why you do it.

🎯 Key takeaways

Polymorphism = same name, different behavior based on the object's type.

It enables flexible code. You can write a function that takes "any PaymentApp" and it'll work with GooglePay, PhonePe, or any new app you create tomorrow — as long as it has a pay() method.

Python is loose about types. Even without inheritance, if two unrelated classes both have a pay() method, Python will call whichever one matches at runtime. This is called duck typing.

Design pattern

Composition

Build complex objects by combining simpler ones. A car has an engine, has wheels, has seats. Each part is a separate object inside the car.

The "has-a" relationship

Inheritance is "is-a." Composition is "has-a". A car has an engine. A computer has a CPU. A human has a heart. The contained things are separate objects with their own properties and methods — the container just uses them.

"Favor composition over inheritance"

This is one of the most repeated pieces of advice in software design. Inheritance creates tight coupling between parent and child — if the parent changes, all children might break. Composition keeps parts independent. If your Engine class changes, your Car class might not even need to know.

Composition in Python

car.py
1class Engine:
2 def __init__(self, horsepower):
3 self.horsepower = horsepower
4 def start(self):
5 print(f"{self.horsepower}hp engine roaring")
6
7class Battery:
8 def __init__(self, kwh):
9 self.kwh = kwh
10
11class Car:
12 def __init__(self, brand, hp, kwh):
13 self.brand = brand
14 self.engine = Engine(hp) # Car HAS-A Engine
15 self.battery = Battery(kwh) # Car HAS-A Battery
16
17 def drive(self):
18 self.engine.start() # delegate to part
19 print(f"{self.brand} moving")
20
21tesla = Car("Model 3", 450, 75)
22tesla.drive()
Output
› 450hp engine roaring
› Model 3 moving

Inheritance vs Composition — when to use which

Inheritance (is-a) Composition (has-a)
Coupling Tight (child depends on parent) Loose (parts are independent)
Flexibility Hard to change behavior at runtime Easy to swap parts
Best for Clear taxonomies (Cat is-a Animal) Building blocks (Car has-an Engine)
Trap to avoid Inheriting just for code reuse Over-fragmenting tiny pieces
🎯 Key takeaways

Composition models "has-a" relationships. When something is part of another thing, compose, don't inherit.

Composition is more flexible than inheritance. You can swap parts at runtime, mix and match, and change implementations without affecting users.

Most real systems use both. Inheritance for true type hierarchies, composition for building things up from parts.
