01 Topic · Route vs Routing

Route vs Routing

Most beginners use these words interchangeably. They're not the same. Get the distinction right and everything about web navigation suddenly makes sense.

The Google Maps analogy

You open Google Maps and search "Charminar." It draws a path from where you are to Charminar — a specific sequence of roads to follow. That single path is a route.

Now think about Google Maps itself. It can find a path from any location to any other location, accounting for traffic, road closures, and your preferred mode of travel. That overall system — the engine that produces routes on demand — is routing.

🗺️ The mental model

Route = a single, specific path. One URL → one handler.

Routing = the whole system that matches incoming URLs to the right handler.

You define many routes. The routing system decides which one applies to each request.

Anatomy of a route

A route is made of three things:

  • HTTP method — what action to perform (GET, POST, etc.)
  • Path pattern — what URL to match (/users/{id})
  • Handler — the function that runs when this route matches

When a request arrives, the routing system looks at all your defined routes and finds the one whose method + path pattern matches. Then it calls that handler.

Static vs dynamic routes

Some routes match exactly one URL: /about, /contact. These are static.

Others have placeholders that match any value: /users/{id} matches /users/1, /users/42, /users/anything. These are dynamic routes, and the placeholders are called route parameters (or path params).

There are also query parameters — the stuff after the ? in a URL. /search?q=chai&limit=10 has two query params. They're optional filters, not part of the route itself.

Client-side vs server-side routing

The same word — "routing" — refers to two completely different things depending on which side you're on:

  • Server-side routing — every URL change makes a new request to the server. The server matches the URL to a route handler and returns HTML. Traditional websites work this way. Express, FastAPI, Django all do server-side routing.
  • Client-side routing — the browser loads the app once, then JavaScript intercepts URL changes and swaps content without a server round-trip. React Router, Vue Router, Next.js (mostly) use this. This is how Single Page Apps (SPAs) work.

Modern frameworks like Next.js mix both: server-side for the first page load, client-side for subsequent navigation.

A route is one URL pattern mapped to one handler. Routing is the system that picks the right route for each incoming request. Static routes match one exact URL; dynamic routes use placeholders to capture values from the URL.

02 Topic · File Handling

File Handling in C & Python

Programs that can't save data are like notebooks that disappear at midnight. File handling is how you make data survive. We'll learn it in both C and Python — and you'll see why most people prefer Python for this.

The notebook analogy

Imagine you have a notebook on your desk. To use it, you have to:

  1. Open it — find the page you want to work on
  2. Read or write — either look at what's there or scribble something new
  3. Close it — put it back when done so the pages don't get dirty

That's exactly how both C and Python treat files. The steps are identical. What differs is how much hand-holding the language gives you and how much it forces you to clean up yourself.

The file modes you'll actually use

The modes are the same in C and Python. This is the one place these languages agree completely:

  • "r" — read. File must exist. Cursor starts at the beginning.
  • "w" — write. Creates a new file or erases the existing one. Cursor at start.
  • "a" — append. Adds to the end of an existing file. Won't erase what's already there.
  • "r+" — read and write. File must exist.
  • "rb" / "wb" — binary read/write. For images, audio, anything non-text.
⚠️ The "w" trap (applies to both languages)

Opening a file in "w" mode erases everything in it instantly — even before you write anything. If you wanted to add to an existing file, you wanted "a", not "w". Beginners lose data to this constantly, in every language.

File handling in C — the manual approach

        
C was designed in the 1970s, and it shows. You manage everything: opening, reading, writing, error checking, and — most importantly — closing. C doesn't clean up after you. If you forget fclose(), you leak a file handle. If your program crashes before reaching fclose(), your buffered writes may never make it to disk.

        

          
file_demo.c

          


1#include <stdio.h>


2#include <stdlib.h>


3


4int main() {


5    FILE *fp = fopen("notes.txt", "w");


6    if (fp == NULL) {            // always check!


7        perror("Failed to open");


8        return 1;


9    }


10


11    fprintf(fp, "Hello world\n");     // formatted write


12    fputs("Second line\n", fp);     // plain write


13


14    fclose(fp);                       // YOU MUST DO THIS


15    return 0;


16}

          

        

        
Reading is even more involved — you allocate a buffer, you tell C how big it is, you check for end-of-file yourself:

        

          
read_demo.c

          


1FILE *fp = fopen("notes.txt", "r");


2if (fp == NULL) { perror("open"); return 1; }


3


4char buffer[256];                       // allocate buffer


5while (fgets(buffer, sizeof(buffer), fp) != NULL) {


6    printf("%s", buffer);             // echo each line


7}


8


9fclose(fp);

          

        

        

          
⚠️ C's responsibilities are YOUR responsibilities

          

            
NULL check after fopen. Skip this and you get a segfault when the file doesn't exist.

            
Buffer size. If a line is longer than your buffer, fgets reads only part of it. You decide the size; you live with the consequences.

            
fclose every time. Including on error paths. Including before return. Including when an exception... oh wait, C doesn't have exceptions, so this part is at least simpler.

          

        

      


      

        
File handling in Python — the clean approach

        
Python was designed 20 years after C, with the explicit goal of being easier to read and write. The Python convention is the with statement (a context manager). It opens the file, gives it to you, and closes it automatically when the block exits — even if an exception happens.

        

          
file_demo.py

          


1# WRITE — creates or overwrites notes.txt


2with open("notes.txt", "w") as f:


3    f.write("Hello world\n")


4    f.write("Second line\n")


5# file is automatically closed here — even on error


6


7# READ — entire file as one string


8with open("notes.txt", "r") as f:


9    text = f.read()


10print(text)


11


12# READ — line by line (better for big files, no buffer size!)


13with open("notes.txt") as f:


14    for line in f:


15        print(line.strip())


16


17# APPEND — adds to the end without erasing


18with open("notes.txt", "a") as f:


19    f.write("Added later\n")

The file pointer (cursor)

        
Every open file in both C and Python has an invisible cursor that marks where the next read or write will happen. When you open a file in read mode, the cursor starts at byte 0. As you read, it moves forward. You can move it manually with seek() in Python or fseek() in C.

Handling errors

        
Files cause errors all the time: file doesn't exist, no permission to read, disk is full. Each language handles this differently.

        

          
error_handling.c

          


1FILE *fp = fopen("settings.txt", "r");


2if (fp == NULL) {


3    perror("Cannot open");     // prints reason


4    return 1;                    // or fall back


5}

          

        

        

          
error_handling.py

          


1try:


2    with open("settings.txt") as f:


3        config = f.read()


4except FileNotFoundError:


5    print("No settings — using defaults")


6    config = ""


7except PermissionError:


8    print("Can't read this — check permissions")

          

        

        
Python's exception-based approach lets you catch specific failure types separately. C forces you to inspect errno or just use perror() to print whatever went wrong.

      


      

        
Text vs binary files

        
Both languages distinguish text and binary modes. If you're storing words, numbers, or human-readable content, use text mode (the default: "r"/"w"/"a"). If you're storing images, audio, PDFs, or non-text data, use binary mode ("rb"/"wb"). Trying to read a JPEG in text mode either crashes or gives you garbled output.

      


      

        
Buffer and Cache — the hidden helpers

        
When you work with files, two concepts silently make everything faster: buffers and caches. They're different ideas, but beginners often confuse them. Let's fix that.


        
Buffer — the holding area before it reaches the destination

        
A buffer is a temporary chunk of memory used to hold data while it's being transferred from one place to another. Think of it like a middleman.


        

          
🚂 Real-world example: Railway station luggage trolley

          

            
Imagine you're at Mumbai CST station. Your train is on Platform 7, but your bags just arrived on the conveyor from the parcel van. A porter collects all bags from the conveyor (buffer) and then makes one trip to Platform 7 — instead of running back and forth for each individual bag.

            
That's exactly what a file write buffer does. Instead of writing each printf() or f.write() call directly to disk (slow!), the OS collects your data in a buffer (RAM), and then flushes it to disk in one efficient batch.

          

        


        

          
📦 Another example: IRCTC ticket booking queue

          

            
On Tatkal booking day at 10:00 AM, lakhs of people click "Book" simultaneously. IRCTC doesn't process each request one-by-one at the same moment — requests go into a buffer queue in memory, and the server processes them sequentially from that queue. Without the buffer, the system would crash instantly.

          

        


        
In C, when you use fgets(buffer, 256, fp) — that buffer[256] array is the buffer. You're telling C: "give me data in 256-byte chunks". In Python, the file object handles buffering for you automatically.


        

          
buffer_demo.py

          


1# Python buffers writes — they may not reach disk immediately


2with open("log.txt", "w") as f:


3    f.write("Line 1\n")    # goes into buffer (RAM)


4    f.write("Line 2\n")    # still in buffer


5    f.flush()            # force flush NOW — don't wait for close


6# 'with' block ends → buffer flushed + file closed automatically

          

        


        

          
⚠️ Why this matters in C (the scary part)

          

            
If your C program crashes before fclose() is called, the buffer may still be sitting in RAM — and your writes never reach disk. This is a real bug that has caused data loss in production systems. Always call fclose() or fflush(fp) before a critical point.

          

        


        
Cache — the shortcut that remembers

        
A cache is a faster storage layer that remembers frequently accessed data so you don't have to fetch it from a slower source every time. Unlike a buffer (temporary transit area), a cache is a permanent-ish storage of previous results.


        

          
🏪 Real-world example: Kirana store near your house

          

            
Think of a kirana (corner shop) in your mohalla. The shopkeeper's godown (warehouse) is 2 km away — that's the hard disk. But he keeps the top-selling items — Maggi, Amul butter, Parle-G — right at the counter. That counter is the cache.

            
When you ask for Parle-G, he grabs it in 2 seconds (cache hit ✅). When you ask for something rare like imported olive oil, he has to send someone to the godown — 20 minutes (cache miss ❌). The cache makes common requests blazing fast.

          

        


        

          
📱 Another example: Zomato app loading restaurants

          

            
The first time you open Zomato, it fetches restaurants from the server (slow — network call). But your browser/app caches that response. The next time you open it, it shows you the cached list instantly, while quietly refreshing in the background. That's cache in action — every app you use does this.

          

        


        
In file I/O, the OS itself maintains a page cache — frequently read file blocks are kept in RAM. If you read the same file twice, the second read is much faster because the OS serves it from the cache rather than going back to disk.

Which one should you learn first?

        
If you're a beginner: start with Python. The syntax is shorter, errors are clear, and you can focus on what file handling does instead of fighting the language.

        
If you're learning systems programming or embedded: learn C's file handling. It's universal in those worlds, and you'll see fopen/fread/fwrite in every codebase from the Linux kernel to firmware.

        
If you're a working developer: know both. You'll mostly write Python (or similar high-level languages), but the day you need to read a binary log file at maximum speed, or interop with a C library, you'll be grateful.

      


      

        
🎯 File handling in one sentence

        

          
The concepts (open, read/write, close, modes, cursor) are identical in C and Python. Python wraps them in a friendly safety net (with blocks, exceptions, no buffer sizes). C makes you manage everything yourself but rewards you with speed and control. Same destination, different journey.

Variable Scope

      
"Why isn't my variable working here? It worked two lines ago!" Welcome to scope — the rules that decide where each variable is visible and where it isn't.

    


    


      

        
The house analogy

        
Think of a house with multiple rooms.

        
    
          
  • The water tank on the roof serves every room. Anyone in the house can use it. That's a global variable — accessible from anywhere.
    • 
          
  • Your personal water bottle in your room is only accessible to you, when you're inside that room. That's a local variable — only exists inside the function (or block) where you defined it.
    • 
          
  • The shared filter in the family kitchen is accessible to family members in the kitchen but not to neighbors. That's an enclosing scope — outer function shares with inner.
    • 
        

        

          
🏠 The mental model

          

            
Scope = "from where in my code can I see this variable?"

            
Variables defined inside a function exist only while that function runs, and only that function can see them. Variables defined outside all functions live for the entire program and everyone can see them — but modifying them requires special syntax.

          

        

      


      

        
Python's LEGB rule

        
When you use a variable, Python looks for it in four places, in this exact order:

        
    
          
  1. L — Local: inside the current function
    2. 
          
  2. E — Enclosing: in the function that wrapped this one (if nested)
    3. 
          
  3. G — Global: at the top level of the file
    4. 
          
  4. B — Built-in: Python's own names like print, len, range
    5. 
        

        
The first match wins. If Python can't find the variable in any of these, it raises a NameError.

The global and nonlocal keywords

        
By default, if you assign to a variable inside a function, Python creates a new local variable — even if a global with the same name exists. This is the most confusing thing about Python scope.

        

          
scope_confusion.py

          


1count = 0  # global


2


3def add_one():


4    count = count + 1  # UnboundLocalError!


5


6# Why? The assignment makes Python think 'count' is local,


7# but it tries to read it before assigning. Error.


8


9def add_one_fixed():


10    global count     # declare we mean the global one


11    count = count + 1  # now works

          

        

        
For nested functions, use nonlocal instead of global when you want to modify a variable from the enclosing function (not the global one).

      


      

        
Shadowing

        
If you define a local variable with the same name as a global one, the local one "shadows" the global. Inside the function, only the local exists. The global is untouched.

        

          
shadowing.py

          


1name = "Aarav"


2


3def greet():


4    name = "Priya"  # shadows global; new local var


5    print(name)     # "Priya"


6


7greet()


8print(name)         # still "Aarav" — global untouched

          

        

        

          
⚠️ Avoid shadowing built-ins

          

            
Don't name variables list, dict, str, type, id, or input. These are Python built-ins. Shadowing them in your function will break things in confusing ways.

          

        

      


      

        
Variable lifetime

        
Local variables exist only while their function is running. The moment the function returns, they're gone — Python's garbage collector reclaims their memory. Globals live as long as the program runs.

        
This is why you can't "return a variable" without actually returning its value. The variable name dies with the function.

      


      

        
🎯 Scope in one sentence

        

          
Python looks up variables using LEGB (Local → Enclosing → Global → Built-in). Assignment inside a function creates a local variable, even if a global with the same name exists. Use global or nonlocal only when you actually need to modify an outer variable — usually a sign you should refactor.

Database Indexing

      
The difference between a query that takes 30 milliseconds and one that takes 30 seconds is usually one missing index. Learn this and you'll save real production systems.

    


    


      

        
The phone book analogy

        
Imagine you have a 500-page phone book and need to find "Sharma, Rohit." Two approaches:

        
    
          
  • No index: open page 1. Not there. Page 2. Not there. Keep flipping until you hit Sharma. If they're on page 410, that's 410 pages of work.
    • 
          
  • With index: the phone book is sorted alphabetically. Open to roughly the middle (M). Sharma comes after M, so jump to roughly three-quarters in. Refine. You find Sharma in maybe 6 jumps instead of 410.
    • 
        

        
That's database indexing in one image. Without an index, the database scans every single row looking for matches. With an index, it uses a sorted lookup structure and gets there in a fraction of the time.

      


      

        
What an index actually is

        
An index is a separate data structure that the database maintains alongside your table. It contains the column values you indexed, kept sorted, along with pointers back to the original rows.

        
Most databases use a structure called a B-Tree (balanced tree). Think of it like a tree where each node has many children. To find a value, the database walks the tree from the root, making maybe 3–4 comparisons total — even in a table with millions of rows.

        

          
📚 The mental model

          

            
Full table scan = read every row. O(N) — gets linearly slower as your table grows.

            
Index lookup = walk a sorted tree. O(log N) — barely slows down even at huge sizes.

            
For 1 million rows, full scan = 1,000,000 checks. Index = ~20 checks.

Types of indexes

        
    
          
  • Primary index — built automatically on the primary key. Every table has one.
    • 
          
  • Secondary index — any extra index you add on other columns. Optional, but where the magic happens.
    • 
          
  • Unique index — like a secondary index, but also enforces that no two rows can have the same value (e.g., email addresses).
    • 
          
  • Composite index — covers multiple columns together. Useful when you search by (last_name, first_name) as one unit.
    • 
          
  • Partial index — only indexes rows matching a condition. Saves space when you only query a subset.
    •

When to add an index — and when not to

        

          
✓ Add an index when

          

            
You frequently search, filter, or join on a column. The column has high cardinality (many distinct values, like email or user_id). The table is large enough that scanning it is slow.

          

        

        

          
✗ Don't add an index when

          

            
The table is small (under a few thousand rows — scanning is already fast). The column has very low cardinality (only 2–3 distinct values, like a "status" column). The table is write-heavy and read-light — every INSERT and UPDATE has to update all indexes too, which costs time.

          

        

      


      

        
The hidden cost of indexes

        
Indexes aren't free. Three trade-offs:

        
    
          
  • Disk space — each index is a separate structure stored on disk. Large tables with many indexes can have indexes that take more space than the data itself.
    • 
          
  • Slower writes — every INSERT, UPDATE, or DELETE on the table also has to update every index. More indexes = slower writes.
    • 
          
  • Maintenance — indexes can become fragmented over time and need occasional rebuilding.
    • 
        

        
The rule: index what you query. Don't index what you don't.

      


      

        
🎯 Indexing in one sentence

        

          
An index is a sorted lookup structure that lets the database find rows by value in milliseconds instead of seconds. Add indexes on columns you search frequently. Don't index everything — each index costs space and slows writes.

SQLite vs MySQL vs PostgreSQL

      
Three databases. Three completely different tools. Picking the right one upfront saves you migration pain later. Here's how they actually differ.

    


    


      

        
The vehicle analogy

        
Think of these databases as vehicles:

        
    
          
  • SQLite = a bicycle. Tiny, simple, no setup. You don't need a license, fuel, or a parking spot. But you can't carry a family or drive on the highway.
    • 
          
  • MySQL = a car. Practical, popular, gets the job done. Most small-to-medium businesses run on this. Comfortable for daily use. Limits show only at very large scale.
    • 
          
  • PostgreSQL = a heavy-duty truck. Built for serious cargo. More moving parts, more maintenance, but it can handle anything you throw at it — and keeps doing so as you grow.
    • 
        

        
All three are SQL databases. All three speak roughly the same query language. But what they're built for is very different.

      


      

        
SQLite — the embedded database

        
SQLite is unusual because it's not a server. It's a library. Your entire database lives as a single file (like app.db) and your application reads/writes that file directly.

        
    
          
  • Zero configuration. No install, no daemon, no port. Just import sqlite3 and go.
    • 
          
  • Single file. The whole database is one file. Easy to back up — just copy the file.
    • 
          
  • Bundled into everything. Every iPhone, Android phone, every browser, every Mac, almost every device ships with SQLite. It's the most deployed database in the world.
    • 
          
  • Limit: only one writer at a time. Two users editing simultaneously? Second one waits.
    • 
        

        

          
📱 Best for

          

            
Mobile apps, desktop apps, browser extensions, IoT devices, prototypes, small websites with low concurrent traffic, embedded systems, local caches, single-user tools.

          

        

      


      

        
MySQL — the popular workhorse

        
MySQL is a full client-server database. It runs as a separate process; your app connects to it over a network. It's been the default choice for web applications for two decades.

        
    
          
  • Battle-tested at scale. Powers Facebook, YouTube, Twitter (early days), countless WordPress sites.
    • 
          
  • Fast reads. Highly optimized for the typical pattern of "many reads, few writes."
    • 
          
  • Big ecosystem. Tools, hosting, tutorials, plugins — everything exists for MySQL.
    • 
          
  • Multiple storage engines. InnoDB (default, transactional) vs MyISAM (older, faster reads but no transactions).
    • 
          
  • Limit: weaker on advanced features compared to PostgreSQL (no complex JSON queries until recently, simpler types).
    • 
        

        

          
🌐 Best for

          

            
Web applications, content sites, e-commerce, SaaS products, anywhere with high read traffic. Particularly strong if you're building on PHP/WordPress, but works with everything.

          

        

      


      

        
PostgreSQL — the powerhouse

        
PostgreSQL (often called "Postgres") is the most feature-rich open-source SQL database. If MySQL is "good enough," Postgres is "best in class."

        
    
          
  • Strict and standard-compliant. Follows SQL standards more closely than MySQL.
    • 
          
  • Advanced types. Native JSON/JSONB, arrays, geographic data (PostGIS), full-text search, custom types — all built in.
    • 
          
  • True ACID transactions with sophisticated isolation levels.
    • 
          
  • Extensible. Add your own data types, operators, even programming languages.
    • 
          
  • Limit: slightly more complex to set up and tune than MySQL. Slightly higher resource usage at small scale.
    • 
        

        

          
🏛️ Best for

          

            
Anything serious. Fintech, healthcare, analytics, geospatial apps, anywhere data integrity is critical, anywhere you need advanced features. Modern startups in 2026 increasingly default to Postgres over MySQL.

        06
        Topic · SQL Query Fundamentals
      

      
SQL Queries

      
SQL is the language every database speaks. Whether you're on SQLite, MySQL, or PostgreSQL — the query syntax is nearly identical. These are the patterns you'll write every single day as a backend developer.

    


    


      

        
Think in tables, not loops

        
In Python you'd loop through a list to find users older than 25. In SQL you describe what you want — the database figures out how to find it efficiently.

        

          
💡 SQL is declarative

          

            
The database query planner automatically decides whether to use an index, which rows to scan, and how to join tables — you just state the result you want.

          

        

      


      

        
SELECT — read data

        
Every query starts here. SELECT names the columns, FROM names the table.

        

          
SQL · SELECT

          


1-- All columns, all rows


2SELECT * FROM users;


3


4-- Specific columns only


5SELECT name, email FROM users;


6


7-- Rename a column with AS (alias)


8SELECT name AS full_name, email FROM users;


9


10-- No duplicates in results


11SELECT DISTINCT city FROM users;

          

        

      


      

        
WHERE — filter rows

        
WHERE limits which rows come back. All comparison operators work (= <> < >), plus SQL-specific ones.

        

          
SQL · WHERE

          


1SELECT * FROM users WHERE age > 25;


2


3-- Combine with AND / OR


4SELECT * FROM users WHERE age > 25 AND city = 'Hyderabad';


5


6-- IN — match any value in a list


7SELECT * FROM users WHERE city IN ('Delhi', 'Mumbai', 'Hyderabad');


8


9-- LIKE — pattern match (% = any chars, _ = one char)


10SELECT * FROM users WHERE email LIKE '%@gmail.com';


11


12-- BETWEEN — inclusive range


13SELECT * FROM orders WHERE amount BETWEEN 100 AND 500;


14


15-- IS NULL — find missing values


16SELECT * FROM users WHERE phone IS NULL;

          

        

      


      

        
ORDER BY · LIMIT · OFFSET — sort and paginate

        

          
SQL · Sorting & Pagination

          


1-- Youngest users first


2SELECT * FROM users ORDER BY age ASC;


3


4-- Biggest orders, top 5 only


5SELECT * FROM orders ORDER BY amount DESC LIMIT 5;


6


7-- Page 2 of 10 results per page (skip first 10)


8SELECT * FROM users ORDER BY id LIMIT 10 OFFSET 10;

          

        

      


      

        
Aggregate functions + GROUP BY + HAVING

        
Aggregate functions collapse many rows into one summary value. GROUP BY runs them per group. HAVING then filters those groups — like WHERE but applied after grouping.

        

          
SQL · Aggregates & GROUP BY

          


1-- The five aggregate functions


2SELECT COUNT(*) FROM users;             -- total row count


3SELECT SUM(amount) FROM orders;         -- total revenue


4SELECT AVG(age) FROM users;            -- average age


5SELECT MAX(amount), MIN(amount) FROM orders;


6


7-- GROUP BY: count orders per user


8SELECT user_id, COUNT(*) AS order_count


9FROM   orders


10GROUP BY user_id;


11


12-- HAVING: only groups with more than 2 orders


13SELECT user_id, COUNT(*) AS order_count


14FROM   orders


15GROUP BY user_id


16HAVING COUNT(*) > 2;

          

        

        

          
⚠️ WHERE vs HAVING

          

            
WHERE filters rows before grouping. HAVING filters groups after aggregation. You cannot use an aggregate like COUNT(*) inside a WHERE clause.

          

        

      


      

        
JOINs — combine rows from two tables

        
A JOIN links rows from two tables on a shared column (usually a foreign key). Four types — each decides what to do when a row has no match on the other side.

        
    
          
  • INNER JOIN — only rows that match in both tables. Unmatched rows from either side are dropped.
    • 
          
  • LEFT JOIN — every row from the left table. If no right-side match, those columns are NULL.
    • 
          
  • RIGHT JOIN — every row from the right table. If no left-side match, those columns are NULL.
    • 
          
  • FULL OUTER JOIN — every row from both tables. NULLs wherever there's no match. (Not supported natively in SQLite.)
    • 
        

        

          
SQL · JOINs

          


1-- INNER JOIN: only matched rows


2SELECT u.name, o.product


3FROM   users u INNER JOIN orders o ON u.id = o.user_id;


4


5-- LEFT JOIN: all users, even those with no orders


6SELECT u.name, o.product


7FROM   users u LEFT JOIN orders o ON u.id = o.user_id;


8


9-- Find users who have placed NO orders


10SELECT u.name


11FROM   users u LEFT JOIN orders o ON u.id = o.user_id


12WHERE  o.user_id IS NULL;

INSERT · UPDATE · DELETE — write data

        

          
SQL · Write Operations

          


1-- INSERT: add a row


2INSERT INTO users (name, email, age)


3VALUES ('Priya', 'priya@example.com', 28);


4


5-- INSERT multiple rows at once


6INSERT INTO users (name, email, age) VALUES


7  ('Arjun', 'arjun@example.com', 24),


8  ('Meena', 'meena@example.com', 31);


9


10-- UPDATE: modify rows — ALWAYS use WHERE


11UPDATE users SET age = 29 WHERE id = 1;


12


13-- DELETE: remove rows — ALWAYS use WHERE


14DELETE FROM users WHERE id = 5;

          

        

        

          
🚨 Never UPDATE or DELETE without WHERE

          

            
UPDATE users SET active = false; deactivates every single user. DELETE FROM users; empties the entire table. Always write the WHERE clause first.

          

        

      


      

        
Subqueries — queries inside queries

        
A subquery is a SELECT nested inside another statement. Use them when you need a dynamic value from the database itself — like the average, or a set of IDs.

        

          
SQL · Subqueries

          


1-- Users older than the average age


2SELECT name FROM users


3WHERE  age > (SELECT AVG(age) FROM users);


4


5-- Users who have placed at least one order


6SELECT name FROM users


7WHERE  id IN (SELECT DISTINCT user_id FROM orders);

          

        

      


      

        
🎯 SQL query order in one line

        

          
SELECT → FROM → JOIN → WHERE → GROUP BY → HAVING → ORDER BY → LIMIT. Not all clauses are needed every time — use only what the query requires.
